# Phase 1 Plan 05: Linear Webhook Receiver Summary

Implemented `POST /webhooks/linear` per CONTEXT.md D-04 / D-08 / D-09 and
RESEARCH.md Pattern 1: HMAC-SHA256 verify with `timingSafeEqual` against
`LINEAR_WEBHOOK_SECRET`, idempotent INSERT into the partitioned
`events.raw_event` keyed on `(source, upstream_id)`, async enqueue of a
`resolve_identity` Graphile Worker job, return 200. Local benchmark: 200
concurrent valid Linear webhooks, p99 = 169ms (< 200ms SLA).

## What Shipped

### Task 1 — Webhook handler + integration tests (commit `dab6f1e`)

`packages/server/src/routes/webhooks/linear.ts` does exactly four things
synchronously:

1. **Validate `Linear-Delivery`** (UUID v4) — 400 with
   `{error:'missing_or_invalid_linear_delivery'}` on missing/malformed
   per D-09. (No fallback synthesis — D-09 hard-fails to surface
   misconfigured proxies rather than silently widening the dedup key.)
2. **HMAC verify** — `createHmac('sha256', LINEAR_WEBHOOK_SECRET).update(req.rawBody)`
   compared with `timingSafeEqual` after an explicit `length` check; 401
   on missing/mismatched signature. Uses `req.rawBody` exclusively (no
   `req.body` reference anywhere in the file — OBS-04 grep guard remains
   green with no special-case annotation needed).
3. **Idempotent INSERT** — via a CTE that:
   - looks up any existing row with the same `(source, upstream_id)`
   - inserts only when `NOT EXISTS`, with the raw bytes
     (`req.rawBody.toString('utf8')`) bound as a TEXT parameter and cast
     to jsonb inside SQL via `($N::text)::jsonb` — guarantees byte-identity
     between the bytes hashed and the bytes stored (T-05-08 mitigation).
   - returns `id` plus a boolean `is_new` so the resolver enqueue is
     gated correctly. The `ON CONFLICT (source, upstream_id, received_at)
     DO NOTHING` clause stays on the INSERT as defense-in-depth for
     tight-concurrency races at microsecond precision.
4. **Enqueue** — `graphile_worker.add_job('resolve_identity'::text, payload::json)`
   with `payload = { raw_event_id, workspace_id }`. **Only** runs on a new
   insert (`isNewInsert === true`); duplicates are not re-enqueued.

`packages/server/src/index.ts` registers the route after `authPlugin` so
it shares the same Fastify instance and decorators (env, db, pgPool).

Tests (3 files, 24 vitest pass):

- `webhook-linear.test.ts` (6 tests):
  1. 200 on valid HMAC + valid Linear-Delivery; row inserted with
     `signature_valid=true`; **raw-body integrity** asserted via
     `JSON.parse(payload::text) === JSON.parse(sentBody)`.
  2. 401 on invalid HMAC.
  3. 400 on missing `Linear-Delivery`.
  4. 400 on malformed (non-UUID) `Linear-Delivery`.
  5. Source-grep: no `resolveIdentity(` call (Pitfall 2 source assertion).
  6. Source-grep: no `req.body` / `request.body` reference (OBS-04).

- `idempotency.test.ts` (1 test): same signed delivery sent 5x → exactly
  1 row in `events.raw_event` for that delivery_id.

- `vitest.config.ts`: `fileParallelism: false` — two integration files
  each calling `migrate()` against a freshly-created DB raced on the
  Postgres system catalog (`pg_namespace_nspname_index`,
  `pg_type_typname_nsp_index`) because `CREATE SCHEMA` / `CREATE TYPE`
  serialise on global catalogs even across DBs. Disabling file
  parallelism (per-test parallelism inside a file remains) eliminates
  the race.

### Task 2 — webhook-ack p99 < 200ms benchmark + Graphile schema at startup (commit `727ac04`)

`packages/server/test/perf/webhook-ack.bench.ts` is the D-31 / INGEST-04
CI gate:

- Drops + recreates `agentwatch_bench`, spawns the server (CI: prebuilt
  `node dist/index.js`; local: `tsx src/index.ts`), waits for `/health`
  to return 200, seeds a workspaces row.
- Pre-generates 1000 unique signed payloads so autocannon doesn't replay
  the same delivery (which would short-circuit on the dedup CTE and skew
  latency low).
- Fires `connections: 200` for `duration: 15` seconds at
  `/webhooks/linear`.
- Asserts `p99 < 200` (literal numeric value) and zero non-2xx
  responses; exits 0 on pass.

`packages/server/src/index.ts` now installs the Graphile Worker schema
at startup via `runMigrations({ connectionString })` from
`graphile-worker`. Without this, every webhook returns 500 because
`graphile_worker.add_job` does not exist until the worker process (plan
01.06) installs it. `runMigrations` is idempotent so dual installation
(web + worker containers) is safe.

`.github/workflows/ci.yml` gains a `bench-webhook-ack` job on a
`postgres:16-alpine` service container. The bench is required for the
foundation phase — a regression is a red build, not a customer-reported
issue.

## Pitfalls Mitigated

- **Pitfall 1 (Linear at-least-once duplicate delivery):** UNIQUE
  constraint exists on `(source, upstream_id, received_at)` from plan
  01.02 + the handler's idempotency CTE keys dedup on `(source,
  upstream_id)` only. 5x-replay test passes with exactly 1 row stored
  and exactly 1 resolver job enqueued.
- **Pitfall 2 (synchronous processing):** handler returns 200 after
  HMAC verify, single INSERT, and a fire-and-forget enqueue. No DB
  joins, no vendor API calls, no resolver runs synchronously. Test
  asserts no `resolveIdentity(` call exists in the source.
- **Pitfall 8 (redelivery storm exhausts pool):** explicit pool size 20
  from plan 01.04 + async-only handler + 200-concurrent benchmark in
  CI. Local bench non2xx=0, p99=169ms.
- **Pitfall 12 (signature header value never logged):** the handler
  does not log `req.headers['linear-signature']` directly; the
  `logWebhookReceipt` plugin (plan 01.04) emits only the D-29 whitelist
  fields; pino redact paths in `index.ts` censor the signature header.

## Deviations from Plan

### Auto-fixed Issues

**1. [Rule 1 — Bug] `(xmax = 0)` is unavailable on partitioned tables**

- **Found during:** Task 1 first integration-test probe.
- **Issue:** the plan's INSERT used `RETURNING id, (xmax = 0) AS is_new`
  to detect new vs. duplicate inserts. Postgres rejects this on a
  partitioned table with `cannot retrieve a system column in this
  context` because the partition router routes through the parent's
  pseudo-row, which has no xmax.
- **Fix:** replaced with a CTE pattern:
  ```sql
  WITH existing AS (SELECT id FROM events.raw_event WHERE source='linear' AND upstream_id=$1 ORDER BY received_at DESC LIMIT 1),
       inserted AS (INSERT ... WHERE NOT EXISTS (SELECT 1 FROM existing)
                    ON CONFLICT (source, upstream_id, received_at) DO NOTHING RETURNING id)
  SELECT id, true AS is_new FROM inserted UNION ALL SELECT id, false AS is_new FROM existing LIMIT 1
  ```
  - The `WHERE NOT EXISTS` guards against re-inserting; the `ON
    CONFLICT` stays as defense-in-depth for tight-concurrency races at
    microsecond precision.
- **Files modified:** `packages/server/src/routes/webhooks/linear.ts`
- **Commit:** `dab6f1e`

**2. [Rule 1 — Bug] Idempotency was broken: `(source, upstream_id, received_at)` UNIQUE never fires for replays**

- **Found during:** Task 1 idempotency probe — 3 sequential identical
  calls produced 3 rows.
- **Issue:** the plan-01.02 schema requires the partition key
  (`received_at`) in the unique constraint. `received_at = now()` is
  different on every replay, so plain `ON CONFLICT (source, upstream_id,
  received_at) DO NOTHING` never deduplicates.
- **Fix:** see deviation 1 — the CTE keys dedup on `(source,
  upstream_id)` directly via `WHERE NOT EXISTS`.
- **Files modified:** `packages/server/src/routes/webhooks/linear.ts`
- **Commit:** `dab6f1e`

**3. [Rule 1 — Bug] `graphile_worker.add_job` overload resolution failed with `unknown` first arg**

- **Found during:** Task 1 first probe.
- **Issue:** the plan's enqueue used
  `add_job('resolve_identity', $1::jsonb)`. Postgres treated the unquoted
  literal as `unknown`, then failed to find a matching overload because
  Graphile's signature is `(text, json)` (NOT `jsonb`).
- **Fix:** explicit `::text` cast on the literal +
  `${payload}::json` (not jsonb) on the param. Final form:
  `SELECT graphile_worker.add_job('resolve_identity'::text, ${payload}::json)`.
- **Files modified:** `packages/server/src/routes/webhooks/linear.ts`
- **Commit:** `dab6f1e`

**4. [Rule 2 — Missing critical functionality] Web container did not install Graphile Worker schema at startup**

- **Found during:** Task 2 first benchmark run — 931 / 2000 non-2xx
  responses, all 500 with `function graphile_worker.add_job(unknown,
  jsonb) does not exist`.
- **Issue:** plan 01.04's bootstrap does not install the
  `graphile_worker` schema; that's planned for plan 01.06. But the
  webhook handler tries to enqueue from request 1 of boot. The worker
  container's eventual startup would create the schema, but the web
  container's webhook returns 500 in the meantime — and worse, jobs
  enqueued during the gap are simply lost.
- **Fix:** added `runMigrations({ connectionString })` from
  `graphile-worker` to the web container's startup, after drizzle
  migrate and before `fastify.listen()`. Idempotent — plan 01.06's
  worker container can call it again without conflict.
- **Files modified:** `packages/server/src/index.ts`
- **Commit:** `727ac04`

**5. [Rule 3 — Blocking] Vitest file-parallel races on Postgres system catalog**

- **Found during:** Task 1 full test suite.
- **Issue:** two integration files (`webhook-linear`, `idempotency`)
  each `DROP DATABASE / CREATE DATABASE` then `migrate()` (which runs
  `CREATE SCHEMA "drizzle"` + many `CREATE TYPE`s). Even though they
  target different DBs, those DDLs serialise on the global `pg_namespace`
  / `pg_type` catalogs, producing duplicate-key errors when forks run
  concurrently.
- **Fix:** added `fileParallelism: false` to
  `packages/server/vitest.config.ts`. Per-test parallelism inside a file
  remains the default.
- **Files modified:** `packages/server/vitest.config.ts`
- **Commit:** `dab6f1e`

**6. [Rule 3 — Blocking] DATABASE_URL_TEST collision between integration files**

- **Found during:** Task 1 full test suite (after fixing #5).
- **Issue:** `DATABASE_URL_TEST` was used directly as the test DB URL by
  both integration files, so when CI sets it, both tests target the same
  database and trample each other's seed data.
- **Fix:** each integration file now honours `DATABASE_URL_TEST` only for
  host/credentials; the path component (DB name) is hardcoded
  per-file (`agentwatch_webhook`, `agentwatch_idem`).
- **Files modified:** both integration test files
- **Commit:** `dab6f1e`

### Architectural Choices Within Plan Scope

- **Bench spawn strategy** mirrors `migrations-on-startup.test.ts`:
  CI=true + `dist/index.js` exists → `node dist/index.js`; otherwise
  `tsx src/index.ts`. The webhook-ack p99 SLA is measured at steady
  state; tsx's startup overhead doesn't bias the histogram.
- **`__resetWorkspaceIdCacheForTests` escape hatch** instead of making
  the cache configurable. The cache is process-scoped in production and
  the test reset is the cleanest way to ensure each test sees a fresh
  workspace lookup without re-architecting the module.
