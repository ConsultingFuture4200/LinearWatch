## Accomplishments

- The Wave-0 placeholder `worker.ts` is replaced with a real Graphile Worker
  process that boots the four P1 tasks and registers three cron schedules.
- `resolve_identity` consumes the jobs the webhook handler (plan 01.05)

  slot is registered so P2 just changes the body.

## Decisions Made

- **Logger-arg order:** `helpers.logger.info(message, meta)` not
  `(meta, message)`. `@graphile/logger` differs from pino here. Caught
  during typecheck on the first GREEN attempt; all four tasks emit log
  lines in `(message, meta)` order.
- **Resolver tolerates missing raw_event:** if the partition got rotated
  between job enqueue and run, the resolver logs a warn and returns —
  it does NOT fail the job. Failing would let Graphile Worker retry the
  poison-pill payload forever.
- **Partition rotation: plain DROP TABLE not DETACH CONCURRENTLY:** the
  partition is past-retention by definition; we are deliberately discarding
  the data. DETACH CONCURRENTLY is for archival, which we do not want.
- **detect_shared_app idempotency via LIKE-on-message:** P1's
  workspace_warnings schema (0000_init.sql section 5) has no structured
  subject column. P2 will sharpen this with real vendor signals; for P1
  the LIKE check on the linear_app_user_id substring inside the message
  is correct and cheap (hourly cron, low volume).
- **refresh_cost_rollup is registered as a stub:** P1 plan says ship the
  cron slot now so P2 only changes the function body. Worker container's
  task list is stable across the P1→P2 boundary.

## Deviations from Plan

### Auto-fixed Issues

**1. [Rule 1 — Bug] Partition-rotation regex never matched the upper bound**

- **Found during:** Task 2 RED test (the manually-fabricated 3-month-old
  partition was NOT being dropped — `to_regclass` returned a non-null
  value after `runJob()`).
- **Issue:** The plan's action specified the regex
  `'TO \\(''([0-9-]+)''\\)'`. After SQL-string un-doubling it becomes
  `TO \('([0-9-]+)'\)`. The actual `pg_get_expr` output for a
  timestamptz-partitioned table is
  `FOR VALUES FROM ('2026-02-01 00:00:00+00') TO ('2026-03-01 00:00:00+00')`
  — there is whitespace and a timezone offset between the date and the
  closing quote, so `[0-9-]+` followed by `'` never matched. Result: the
  upper_bound column came back NULL for every row, the for-loop's
  `if (upper < cutoff)` short-circuited, and the DROP branch was never
  exercised. Pitfall 8 mitigation would have silently failed in
  production once a partition aged past the retention boundary.
- **Fix:** Changed regex to `'TO \\(''(\\d{4}-\\d{2}-\\d{2})'` — match
  only the YYYY-MM-DD prefix and ignore the trailing time + offset.
  Verified empirically with `regexp_match` on a real
  `pg_get_expr` output before re-running the test.
- **Files modified:** `packages/server/src/tasks/rotate-raw-event-partitions.ts`
- **Verification:** Test "drops partitions whose upper bound is more than
  30 days in the past" now passes; `to_regclass(events.raw_event_2026_02)`
  returns NULL after rotation.
- **Committed in:** `4e51fb8` (Task 2 commit).

**2. [Rule 1 — Bug] Logger argument order was reversed in the planned action**

- **Found during:** Task 1 GREEN — first typecheck.
- **Issue:** The plan's action used pino-style
  `helpers.logger.info({ ...meta }, 'message')`. `@graphile/logger`'s
  signature is `info(message: string, meta?: LogMeta)` — message FIRST.
  TypeScript caught this with TS2345 on every logger call.
- **Fix:** Reordered all `info`/`warn` calls in the four task files and
  worker.ts to `(message, meta)`.
- **Files modified:** `packages/server/src/tasks/resolve-identity.ts`,
  `packages/server/src/tasks/rotate-raw-event-partitions.ts`,
  `packages/server/src/tasks/detect-shared-app.ts`.
- **Verification:** `pnpm --filter @linearwatch/server typecheck` clean;
  worker boot smoke test emits the expected message strings.
- **Committed in:** `f94f9c7` (Task 1 commit).

**3. [Rule 3 — Blocking] worker.ts pino redact path tripped OBS-04 grep guard**

- **Found during:** Task 3 acceptance check
  (`bash scripts/check-no-req-body.sh`).
- **Issue:** `worker.ts` configures pino with the same redact paths as
  `index.ts`, including the string `'req.body'`. The OBS-04 grep guard
  matches that literal but exempts lines tagged `// allow-req-body:`
  (which `index.ts` already had).
- **Fix:** Added the same `// allow-req-body: pino redact path string
  (Pitfall 5)` annotation to the worker's redact-paths array.
- **Files modified:** `packages/server/src/worker.ts`.
- **Verification:** `bash scripts/check-no-req-body.sh` returns OK.
- **Committed in:** `5791632` (Task 3 commit).

## Pitfalls Mitigated

- **Pitfall 2 (synchronous resolver):** confirmed reaffirmation — webhook
  handler (plan 01.05) only enqueues; resolver runs async in this worker.
  No `resolveIdentity(` call in `routes/webhooks/linear.ts`.
- **Pitfall 6 (shared OAuth app silent merge):** `detect_shared_app` cron
  surfaces a workspace_warnings WARNING when one `linear_app_user_id`
  shows ≥2 vendor contexts in 24h. The dashboard banner (plan 01.09 / P2)
  reads from this table.
- **Pitfall 8 (partition rotation skipped):** `rotate_raw_event_partitions`
  cron `0 0 1 * *` with `backfillPeriod: 86_400_000` ensures the rotation
  runs even after a brief outage at the month boundary. CREATE TABLE IF
  NOT EXISTS + DROP TABLE IF EXISTS for past-retention partitions —
  no DELETE-FROM anti-pattern.

## Threat Surface Assessment

No new attack surface beyond the plan's `<threat_model>`. Dispositions
T-06-01 through T-06-07 hold:

- **T-06-01** (resolver double-runs): UNIQUE (workspace_id, raw_event_id)
  + ON CONFLICT DO NOTHING; verified by idempotency test (3× → 1 row).
- **T-06-02** (forged confidence): formula reads only actor.id presence
  (binary), so a forged payload lands at confidence 0.5 → PENDING_CONFIRMATION
  → human gate. HMAC at the webhook (plan 01.05) is the actual gate.
- **T-06-03** (long-running resolver blocks queue): each job touches one
  row; concurrency 5; pollInterval 1000ms.
- **T-06-04** (worker logs payload values): pino redact paths replicated
  from web container; resolver logs only {workspace_id, linear_app_user_id,
  confidence, state} — never raw payload values.
- **T-06-05** (rotation skipped after restart): backfillPeriod 86_400_000.
- **T-06-06** (DROP TABLE injection): partition identifiers come from
  `pg_class.oid::regclass` which Postgres server-side-escapes; CREATE
  uses `format(%I)`. No user-controlled string ever becomes an identifier.
- **T-06-07** (warning leaks linear_app_user_id): accepted — single-tenant
  in P1, the user ID is internal to the workspace's own Linear OAuth app.

## Next Plan Handoff

Plan 01.07 (query API skeleton) reads from `identity_mappings` to return
agent rows for the cost dashboard's "Unconfirmed" badge (D-17). The
contract from this plan:

- Every resolved Linear AgentSession event has at least one row in
  `identity_mappings` keyed on `(workspace_id, raw_event_id)`.
- Rows in state `PENDING_CONFIRMATION` are the ones the dashboard side
  panel surfaces for human one-click confirmation.
- Rows in state `NEW_AGENT` had no `actor.id` and need investigation
  (likely a misconfigured or non-AgentSession Linear event).

Plan 01.09 (confirm UI) writes to `identity_mappings.state = 'CONFIRMED'`
and `confirmed_at = now()` for the row the user confirmed. The resolver
in this plan does NOT update existing rows on re-run; the confirm path
is the only writer for `state = 'CONFIRMED'`.
